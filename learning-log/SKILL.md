# Learning log

Look forward: try the ideas you want to act on. List each idea as a hypothesis, write the prediction before each test, record what happened and decide keep, revise or kill. Ideas nobody has tested yet are flagged.

Family: Experimentation · Format: .xlsx · Domain: core

## What it is

A learning log records the tests you run on ideas before you commit to them. Each idea is written as a hypothesis with a direction and a size. Before each test you write what you expect to see; afterwards you record what happened, whether the prediction held, and the decision: keep, revise or kill. Any idea nobody has tested yet shows up as untested. It differs from an evidence register, which looks back at claims already being made and asks what proof exists; a learning log runs new tests and compares the prediction with the result.

## When to use it

Use it when:

- Several hypotheses or ideas are circulating about what would actually improve something, and you want an honest record of which have real tests behind them.
- A test has already run and produced a real result, and you want to record what it actually recommends — keep, revise, or kill — rather than letting a promising-sounding result stand in for a clear verdict.
- You want to know which hypotheses have never been tested at all, not just which ones feel intuitively right.

Not when:

- You don't have a real hypothesis to test yet — this log tracks tests against hypotheses already named, it doesn't generate new ones.
- The idea is genuinely trivial or reversible with no real cost to just trying it — the overhead of a formal test isn't worth it yet.

## How to fill it in

- **scopeNotes** — Say which ideas or hypotheses this log covers — a campaign, a product area, a quarter. A clear boundary tells you which tests belong here.
- **hypotheses** — List every hypothesis you want tracked, including ones you haven't tested yet. Write each as something a test could prove wrong, with a direction and a size — "a shorter form will raise sign-ups by a fifth", not "improve the form".
- **tests** — For each test, write the prediction first, before you run it: what you expect to see, and how big, if the hypothesis is right. Then say how big the test is (how many, over how long), what actually happened and whether the prediction held. Take the result from the data or the people who ran the test, and record it even when it disappoints — a failed test is still something learned. Finish with what you learned, your decision (keep, revise or kill) and the next test it points to.
- **narrative** — Write a few sentences on what the log shows: which hypotheses held, which failed, and which have never been tested. Use only what's recorded.

## What good looks like

The example below tests two of three claims about Line 2's recovery, one on on-time shipments and one on changeover time, each with its prediction written first. Switching the sequencing rule off on one shift for a week dropped that shift's on-time rate to 81% (38 of 47 shipments) while the other shift held at 93%, so the prediction held and the rule stays; the 9 late shipments are why the learning adds the stop rule the test should have had. A new cleaning fixture cut changeovers from 45 to 41 minutes against a predicted 38, on 8 changeovers with one operator, so it is revised and re-tested with all three operators. The third claim, that keeping the queue board current cuts unplanned changeovers from about three a shift to two or fewer, hasn't been tested yet.

## Common mistakes

- **Treating a promising-sounding result as an automatic 'keep' without a real recommendation.** — A result can be real and still be too small, too narrow, or too confounded to fully validate a hypothesis — the recommendation should name that honestly (often 'revise') rather than rounding a partial result up to a clean pass.
- **Leaving a hypothesis off the log because you're confident it hasn't been tested.** — An unlisted hypothesis can't be flagged as untested — naming it and letting it show up with zero tests is exactly how this tool surfaces the gap plainly instead of hiding it by omission.
- **Running a test but never recording what it actually recommends.** — A test with a result but no recommendation leaves the real decision — keep, revise, or kill — unmade, which is the entire point of running the test in the first place.
- **Running a test that can hurt customers with no stop rule.** — Switching a safeguard off is sometimes the only fair test, but write down, with the prediction, the point at which you stop early and switch it back on.

## What it connects to

Upstream:

- **Evidence register** (`evidence-register`) — A claim the evidence register logs as unverified is often exactly the hypothesis this log should go test properly, instead of leaving it to stand as an assumption.

Downstream:

- **A3 problem solving** (`a3`) — A test that recommends 'kill' on a countermeasure hypothesis is a direct signal an A3's own effect-confirmation plan should act on, not quietly ignore.
- **Improvement kata storyboard** (`improvement-kata-storyboard`) — The learning log tracks hypotheses across many efforts; the step-by-step experiments toward one target condition, each with its prediction written first, live on an Improvement kata storyboard.
- **Work instruction** (`work-instruction`) — A kept change becomes the new standard: write it into the work instruction so the next shift does it the tested way.
