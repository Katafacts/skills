# Work instruction

Major steps, each with a key point for how to do it right and the reason it matters — the classic job-instruction shape, so a routing rule or a new process actually works the same way no matter who's running it.

Family: Standard work · Format: .xlsx · Domain: core

## What it is

A work instruction is the classic three-column job instruction: major steps, key points (how to do each step right — a technique, a quality check, a safety point), and the reason each key point matters. It is what lets a new team member, or someone covering, do the task the same way as the person who has done it for years, and it is what you train against.

## When to use it

Use it when:

- A task needs to work the same way regardless of who's doing it — a new hire, a fill-in, or the usual owner.
- A change (a new routing rule, a new process) only works if everyone actually knows the specific technique behind it, not just the headline step.
- You want to see honestly which steps still have no real key point — meaning they're not yet ready to train someone on.

Not when:

- The task is genuinely simple enough that every step is self-explanatory — forcing key points onto a trivial task adds noise, not clarity.
- You're still figuring out the process itself — map it first (a Makigami or a SIPOC), then write the instruction once it's settled.
- The 'key point' would just restate the step — a real key point adds a technique or judgement call the step alone doesn't convey.

## How to fill it in

- **purpose** — Write what this task achieves and why it matters — for the customer, the next step or safety — in one or two sentences.
- **steps** — List the major steps in order, each as a short verb-led phrase, with the minutes it takes when done well. Under each step add the key points — what makes it safe, right or easier — mark each one's kind (safety, quality or ease), and give the reason it matters. Write them while watching someone skilled do the task, not from memory; a step with no key point yet is fine, but mark it so it gets filled. Finish with "done when": what the finished result looks like, so the person knows when the task is complete.
- **narrative** — Write a short note on how to use this instruction: who it's for, the one or two key points most often missed, and when it was last checked against the work.

The example below is a support team's instruction for triaging a support ticket from a customer whose renewal is at risk: four steps, about 12 minutes of hands-on work, five key points each with its kind and reason, and a clear "done when". ## Common mistakes

- **Writing a key point with no reason attached.** — An unexplained rule is just something to memorize — under pressure, people revert to what makes sense to them unless they understand why the rule exists.
- **Forcing a key point onto every step even when a step is genuinely simple.** — Padding a simple step with an invented key point buries the steps that actually need careful technique under noise that doesn't.
- **Writing steps that are really just a restated process map, not actions a person performs.** — A work instruction trains someone to do the task — a step must be something to actually do, not a category or a phase name.

## What it connects to

Upstream:

- **RACI (responsible, accountable, consulted, informed) chart** (`raci-chart`) — Says which role does each task; the work instruction then says how that role does it.
- **Spaghetti diagram: walking and carrying paths** (`spaghetti-diagram`) — After a layout change, the new shorter path and where things are kept go into the work instruction so it holds.
- **Kaizen event charter** (`improvement-event-charter`) — A new process or routing rule set up by a kaizen event often needs a work instruction to actually stick once the event team moves on.
