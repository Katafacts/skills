# Value hypothesis

Once discovery has named a buyer's needs, show why your offer is worth it: each need in their words, what your offer changes for them, and a number in their own figures that proves the value, laid out like a critical to quality (CTQ) tree, with any need still missing proof named plainly.

Family: Voice of the customer · Format: .xlsx · Domain: commercial

## What it is

A value hypothesis closes the same gap a CTQ tree always closes — between 'the customer wants X' and something specific enough to build a case around — pointed at a single deal instead of a product line. It is a three-level tree. At the top, a buyer need, traced to a real discovery call. Under it, what we change: the specific change your offer makes to how the buyer works that meets the need, such as flagging a deal as soon as it goes quiet. Under that, a value measure: today's figure and a target, in the buyer's own units. 'We'll save them time' isn't a value hypothesis — 'time from a deal going quiet to being flagged at risk, under 48 hours versus about 3 weeks today' is. The tree also tracks its own coverage: any need with no value measure yet is named directly, not silently treated as done.

## When to use it

Use it when:

- You have real buyer needs from an actual discovery call and want to translate them into something specific enough to build a business case around, not just a pitch.
- You want to know exactly which parts of your pitch are backed by a real number and which are still just a confident-sounding claim.
- The deal is heading toward a business-case or ROI conversation and you want the value stated as a measure the champion can defend internally, not a slide you presented.

Not when:

- You don't have a real discovery conversation yet, just an assumed persona's pain points — run discovery first, or you'll be quantifying value for a need nobody actually confirmed.
- You want the raw notes from the call — that's the discovery call itself; a value hypothesis assumes the need is already named and is translating it into something measurable.
- The value measure you're about to write is really just a restated benefit ('saves time', 'reduces risk') — push for a real number or concrete criterion before treating it as specified.

## How to fill it in

- **scope** — Name the deal or buyer this is for and where the deal stands now. Write one per buyer; what one buyer values won't hold for the next.
- **needs** — List each buyer need in the buyer's words, traced to something said in a discovery call. Under each need write what we change: the specific change your offer makes that meets it. Under each change write a value measure in time, money or risk, with today's figure and a target, ideally in the buyer's own figures. A change with no value measure under it is a claim the buyer can't check.
- **coverage** — Calculated from the tree — don't type it; check the counts match what you wrote, and look hardest at any need shown with no value measure.
- **narrative** — Write a few sentences on which needs are well supported and which still need more discovery. Base it on the tree, not on what you hope the buyer thinks.
- **nextSteps** — List what you'll do about a gap or a specific need — often a question for the next call — ranked by impact and effort, each with an owner and a date. Tie every step to a named need. Include one step that agrees how and when each value measure will be checked after go-live, counted the same way as today's figure: until then every value measure is a prediction, and the check is what turns it into proof.

## What good looks like

The example below is a value hypothesis for Northline Freight, a mid-market freight company whose sales team finds out about stalled deals about three weeks too late. Every need traces to the discovery call with their revenue operations team, and every figure the case rests on is the buyer's own; the one estimate, about 20% of stalled deals with a reason logged, is labelled as ours. The first need, losing deals that go quiet, carries the money: $310K of pipeline lost in a year, with flagging quiet deals within 48 hours as what we change. How much of that was winnable is still an assumption, so the first next step agrees it with the buyer, and asks for their margin, before any business case is built. The second need is the RevOps lead's 4 hours a week building the pipeline review by hand. A third need, trusting a new system over the familiar spreadsheet, came up only as an aside, so it is left with no value measure rather than guessed. The last next step treats every value measure as a prediction: it agrees how each will be checked 30 days after go-live, counted the same way as today's figure.

## Common mistakes

- **Writing a change or value measure that's really just a restated benefit.** — "Saves the team time" as a value measure has no target and can't be defended in a budget conversation — "time to flag an at-risk deal, under 48 hours versus 3 weeks today" can. A value hypothesis that isn't concrete enough to fail against isn't actually one.
- **Treating a coverage gap (a need with no value measure) as good enough to bring into a business case.** — A need with no change or value measure beneath it is still just a claim, not evidence — the whole point of this tool is surfacing that gap honestly rather than letting an unproven benefit pass as done.
- **Writing needs that aren't traced to a real discovery conversation.** — A value hypothesis translates real buyer needs into value measures — starting from an assumed persona's pain risks building a precise, confident case for something this particular buyer never actually said mattered.

## What it connects to

Upstream:

- **Discovery call standard work** (`discovery-standard-work`) — A need surfaced with real technique in discovery — the compelling event, the cost of inaction — is exactly the kind of evidence this tree exists to translate into a value measure.

Downstream:

- **Deal A3 — win-rate root cause analysis** (`deal-a3`) — When a value hypothesis's value measure turns out to be wrong or unpersuasive after the deal is lost, that gap is exactly what an eventual deal A3's root cause analysis would trace back to.
- **Message architecture** (`message-architecture`) — Once a value measure actually works in a real deal, this is where it gets promoted into the standing message every deal and channel should use — not invented fresh a second time.
- **Business case builder** (`business-case-builder`) — Agree the winnable share of each value measure here first; the business case then puts the buyer's own figures behind it for their finance team.
- **Proof point inventory** (`proof-point-inventory`) — A value measure checked after go-live, in the buyer's own figures, is a proof point: log it with its source and ask the buyer before it is used outside the company.
