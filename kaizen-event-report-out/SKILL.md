# Kaizen event report-out

Close the event week honestly and keep it open until the result has held: the charter's measures before and after on the same yardstick, what was changed, every open action with one owner and a date, and the 30-, 60- and 90-day checks. Hit or missed, held or slipped, overdue actions and missed checks are computed, not typed in.

Family: Kaizen events · Format: .xlsx · Domain: core

## What it is

A report-out is what a kaizen event team shows the sponsor and the process owner on its last day, and then keeps up to date until the result has proved it can last. It answers five questions. Did the measures move? Each of the charter's measures, with its baseline, its target and the result at the report-out, measured the same way as the baseline and with the data it rests on. What was changed? Each change, and the standard it is now written into. What's left? Every action the event didn't finish, each with one owner, a due date and a status. Did it hold? A reading of every measure at the 30-, 60- and 90-day checks, booked before the team leaves. And what did the team learn? The few things it would do differently next time. The last day of an event is the worst day to judge it: the whole team is at the work, everyone is watching and the new way has run a handful of times. The report-out is built to resist that. It won't count a result measured on a different yardstick, it asks for the data behind every number, and it keeps the follow-up visible until the 90-day check, by which time the event team has moved on and the process owner is on their own. Whether each result hit its target, how each check reading compares with the baseline, the target and the report-out result, which actions are overdue and which checks were missed are all worked out for you.

## When to use it

Use it when:

- It's the last day of a kaizen event and the team is about to report to the sponsor and hand the result to the process owner.
- An event finished a few weeks ago and you want one place that says whether its actions closed and its result held.
- A follow-up check is due and you need the measures, actions and dates in front of you to run it.
- Someone is about to copy an event's changes elsewhere and wants to know what the event really achieved, not what it claimed on day 3.

Not when:

- The event hasn't happened yet. Agree the measures, yardstick and check dates on a kaizen event charter first; this report reads its measures from there.
- You want to check whether each new practice is still how the work is done. That is the sustainment audit, run at the 30- or 90-day check; bring its findings back here.
- The work left is a rollout across several teams over months. Sequence it on an implementation plan and keep a single action here that points to it.
- A one-person fix with no event behind it. Log it on the countermeasure log; a report-out for it is ceremony.

## How to fill it in

- **event** — Say what the event worked on, its first and last day, and where its charter is. Name the process owner, the person who runs the process every day after the event and keeps the result, and the sponsor. Record the sponsor's decision at the report-out in one word and one line of why: accept the result, extend the event's work to an agreed date, or escalate what the team can't fix itself. Set the status date to today, and change it every time you update the report: overdue actions and missed checks are counted from it.
- **measures** — Copy each measure from the charter: its unit, which way is better, its baseline, its target and exactly how it is measured. Enter the target as the worst value that still counts, because a result equal to the target is a hit: if the charter says under 25 minutes and you log whole minutes, enter 24; a guard measure that must stay at 2 enters 2 (the source, where the clock starts and stops, and which statistic). Enter the result at the report-out and the data behind it: which runs, how many, when, and the values if there are only a few. Then answer honestly whether it was measured the same way as the baseline. A tempting number on a different yardstick (gun off to gun on instead of last good part to first good part) is not the result; mention it if you like, but don't report it. Keep a guard measure, one that must not get worse, so a gain on one number can't hide a loss on another.
- **changes** — List each change the event made, written as something you could see someone doing, and the standard it is written into: the routine card, the work instruction, the layout drawing. Give each a status. In the standard: written in, and the standard named. Not yet: still to be written in, which is the only status flagged, so add an action to get it there. Withdrawn: taken back out, or deliberately left out, with the reason written beside it; a change pulled off the card because it didn't work, or sent to a storyboard to understand first, is an honest decision, not a gap. Changes that live only in the heads of the event team are the first to drift, especially on the shifts that weren't at the event.
- **actions** — List everything the event didn't finish. Give each action one person's name as owner (not a team, not two names) and a due date, usually within 30 days. Set the status as it changes: Done with the date, or Dropped with the date and the reason in the note. Dropping an action openly is fine; leaving it open and late is not, because it teaches everyone that report-out actions are optional. The report shows each action's status now and on the day each check was booked for. An action raised later, at a follow-up check, gets the date it was raised and shows only from that check on.
- **checks** — Book the 30-, 60- and 90-day checks with the process owner and the sponsor before anyone leaves the report-out; Due by suggests each date, counted from the last day and moved off a weekend. At each check, enter the date it was held and each measure's reading, measured the same way as the baseline. Each reading is marked held (on target, or at least as good as the report-out), slipped (better than the baseline but worse than both) or lost (back at the baseline or worse). A measure nobody read at a held check shows as not measured.
- **learned** — Write the few things the team learned: what it would do differently in the next event, and what it found out about the process. Add to it at each check; the follow-up usually teaches more than the week did. Then write the next step: what happens now, who owns it and by when, including when the report is closed and the measure handed to the team's normal board.
- **summary** — Nothing to enter: the report counts the measures on and off target, the actions done, open, overdue and dropped, the checks held and missed, and the changes not yet in a standard. Each measure is checked for a missing baseline, target or direction, no result, no data behind the result, a different or unconfirmed yardstick, and a missing reading. Each action is checked for no owner, two owners, no due date, a closed action with no date and a drop with no reason. Each change is flagged when it is not yet in a standard, marked in the standard with none named, or withdrawn with no reason. Each check is flagged when no date is booked.

## What good looks like

The example below is the report-out of the 10–12 March changeover event at the Line 2 paint booth, as the line supervisor keeps it up to date at the 90-day check on 10 June. At the report-out, 2 of the 3 charter measures were on target: fetching-and-waiting minutes were 2 against a target of 3 (baseline 14), and changeovers per shift stayed at 2. Changeover time was 27 minutes against the charter's under 25, entered as 24, the worst value that still counts (baseline 45), so missed. The team reported 27, the middle of its 4 changeovers on the baseline's yardstick (one fewer than the charter's 5, and the data note says so), rather than the 19 minutes gun off to gun on. The sponsor's decision on day 3 was to extend the event: not finished, actions running on to the 30-day check. The checks tell the real story. At the 30-day check (booked for 13 April, held on 16 April with the sustainment audit), changeover time was 46 minutes: lost, back above its baseline, and nobody timed the fetching minutes, so that reading is missing. It had slipped to 36 at the 60-day check and 35 at the 90-day check: better than the baseline but short of both the report-out and the target. The other two measures held at both later checks. Of 6 actions, 4 are done (the booth's own cart six weeks late, and the log form's end-time box, added from the audit), 1 was dropped on purpose at the audit with the reason written down, and 1 is overdue: trying the cleaning fixture on the second gun model, re-dated at the audit to 30 April with Marcus Webb as owner and now 41 days late. 2 actions were overdue at the 30-day check and 1 at each check after. Of 4 changes, 2 are in the standard and 2 were withdrawn on purpose, each with its reason: the cleaning order agreed on day 2 never reached the card and went to the changeover storyboard, and the fixture came off the card until it fits both gun models. None is flagged, because none is simply waiting to be written in. The team's learning starts there: about a third of the old 45 minutes (14) was fetching and waiting, an event-week result is a best case, and the charter's open risk, no second-shift operator at the event, is exactly where the cleaning order failed. The next step closes the follow-up and moves changeover time, at 35 minutes against its under-25 target, to the changeover storyboard and the line's board.

## Common mistakes

- **Reporting the best number instead of the baseline's yardstick.** — On day 3 there is always a flattering measure to hand: booth-stopped time instead of last good part to first good part, the best run instead of the middle one. Before and after can only be compared if they were measured the same way. Report the result on the charter's yardstick, and say which runs it rests on.
- **Treating the report-out as the finish line.** — Four runs with the whole team watching are a best case. The result that matters is the one the process owner gets alone at 30, 60 and 90 days. Book the checks before anyone leaves and keep this report open until the last one.
- **Actions owned by "the team", by two people, or with no date.** — Each owner assumes the other has it, and an action with no date is never late, so it never gets done. One name and one date per action, and a status that changes when it closes.
- **Changes that never reach the standard.** — A change agreed in the room but missing from the routine card survives only as long as the people who were in the room remember it, and not at all on a shift that wasn't there. Write every change into a standard, or give it an action that does.
- **Running the event with a readiness risk still open.** — A charter's open readiness item, such as a shift with nobody released to the event, is where the result later fails: the people left out keep their own way of working. Treat an open readiness risk as a reason to move the event, not a note to carry into it.
- **Skipping a reading because the check was busy.** — The measure nobody re-measured is usually the one that slipped. Read every measure at every check, the same way, and let a gap show as a gap.
- **Leaving late actions open forever.** — An action 80 days overdue tells everyone the list doesn't matter. Re-date it with its owner or drop it openly with the reason; both are honest, silence isn't.

## What it connects to

Upstream:

- **Kaizen event charter** (`improvement-event-charter`) — The charter sets the measures, their baselines, targets and exactly how each is measured, and the 30-, 60- and 90-day check dates. The report-out reads them from there and holds the event to them.
- **Implementation plan** (`implementation-plan`) — When some of the event's changes are rolled out across other teams, that rollout lives on an implementation plan; the report-out keeps one action pointing to it and reads its finished milestones as actions done.

Downstream:

- **Sustainment audit** (`sustainment-audit`) — At the 30- or 90-day check, the audit goes to the work and checks each change is still how it's done. Its readings and slips come back here as the check's readings and actions.
- **Countermeasure log** (`countermeasure-log`) — Once the event team has gone, put each open action on the team's countermeasure log, so it is followed up at the huddle every day and not only at the next check.
- **Run chart** (`run-chart`) — Three check readings can mislead. Plot the measure week by week on a run chart with the event marked, and judge whether the result really held against its ordinary ups and downs.

## Where AI helps

Judgement — stays with you:

- Deciding whether a result was really measured the same way as the baseline
- Deciding whether to re-date an overdue action or drop it
- Deciding when the follow-up is finished and the measure goes to the team's normal board

Analysis — AI helps:

- Spotting a result quoted on a different yardstick from the charter's
- Turning event notes into a first list of changes and open actions with owners
- Reading the check results alongside the actions to suggest which change stopped holding

Drudgery — automated:

- Comparing each result with its target, and each reading with the baseline, target and report-out result
- Working out the check dates and which actions were overdue on each
- Counting what is done, open, overdue and dropped, and exporting the workbook
